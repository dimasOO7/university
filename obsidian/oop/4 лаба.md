## 1. Расширенный класс. Конструкторы расширенных классов. Порядок выполнения конструкторов.

### 1.1. Расширенный класс (`extends`)
- **Определение**: В Java механизм наследования реализуется через расширение классов с помощью ключевого слова `extends`. Класс, объявленный с `extends`, называется **расширенным** (*производным*, *дочерним*, *подклассом* / *subclass*), а класс, от которого наследуют, — **базовым** (*родителем*, *суперклассом* / *superclass*).
  ```java
  class SuperClass { /* члены базового класса */ }
  class SubClass extends SuperClass { /* унаследованные + собственные члены */ }
  ```
- **Одиночное наследование**: В Java поддерживается строго **одиночное наследование классов** — класс может непосредственно расширять только один базовый класс (`class B extends A`). Множественное наследование классов запрещено во избежание неоднозначностей (проблема «ромба»). Корень всей иерархии типов — класс `java.lang.Object`.
- **Семантическое отношение «IS-A» («является»)**:
  - Объект расширенного класса *является* специализированным представителем базового типа.
  - В коде это выражается полиморфизмом включения (принцип подстановки Лисков, LSP): везде, где ожидается ссылка на базовый тип, можно передать ссылку на производный класс.
- **Контракт класса и формы наследования**:
  - *Контракт класса* — это совокупность открытых (`public`/`protected`) полей и методов с описанием их семантики и инвариантов.
  - *Наследование типа (контракта)* — производный класс приобретает тип базового класса и может использоваться полиморфно.
  - *Наследование реализации* — производный класс приобретает готовые тела методов базового класса.
  - Основная цель наследования — **специализация**: уточнение и расширение возможностей базового типа под конкретную задачу.

### 1.2. Конструкторы расширенных классов
- **Принцип делегирования полномочий**:
  - Конструкторы **не являются методами и не наследуются** производным классом.
  - Объект производного класса содержит как унаследованные поля базового класса, так и собственные поля.
  - Производный класс не должен напрямую инициализировать базовые поля (они могут быть `private` или требовать сложных проверок). Поэтому конструкторы расширенного класса **обязаны передавать полномочия** по инициализации базовой части конструкторам базового класса.
- **Явный вызов конструктора предка (`super(...)`)**:
  - Для вызова конструктора суперкласса используется ключевое слово `super(...)` со списком аргументов.
  - **Правило первой строки**: вызов `super(...)` обязан быть **строго первой исполняемой инструкцией** в теле конструктора подкласса.
  - В аргументах `super(...)` запрещено использовать ссылку `this` и обращаться к нестатическим полям или методам класса, так как базовый объект ещё не сконструирован.
- **Вызов конструктора текущего класса (`this(...)`)**:
  - Конструктор может вызывать перегруженный конструктор своего же класса через `this(...)`.
  - Вызов `this(...)` также обязан быть только в первой строке конструктора. В одном конструкторе нельзя одновременно вызвать и `this(...)`, и `super(...)`. Цепочка `this(...)` обязана в итоге завершиться конструктором, вызывающим `super(...)`.
- **Автоматический вызов базового конструктора по умолчанию**:
  - Если в первой строке конструктора производного класса **нет** явного вызова `super(...)` или `this(...)`, компилятор Java **автоматически вставляет** вызов базового конструктора без параметров: `super();`.
  - **Обязательное требование к базовому классу**: в базовом классе обязан существовать доступный конструктор без параметров (конструктор по умолчанию либо явно объявленный конструктор без аргументов). Если в базовом классе объявлен только конструктор с параметрами, а в подклассе не вызван явный `super(args)`, компилятор выдаст **ошибку компиляции**.

### 1.3. Порядок выполнения конструкторов и этапы инициализации
При создании экземпляра производного класса (`new SubClass()`) среда выполнения строго соблюдает следующую последовательность:

1. **Этап 0. Выделение памяти и обнуление**:
   - В куче (Heap) выделяется единый блок памяти под все поля (и базовых классов, и производного).
   - Всем полям присваиваются значения по умолчанию: числовые типы — `0`/`0.0`, `boolean` — `false`, ссылки — `null`.
2. **Этап 1. Восходящая раскрутка цепочки вызовов (снизу вверх)**:
   - Конструктор `SubClass` через `super(...)` передает управление конструктору `SuperClass`.
   - Цепочка доходит до вершины иерархии — конструктора `java.lang.Object`.
3. **Этап 2. Нисходящая инициализация и выполнение тел (сверху вниз, от `Object` к конечному потомку)**:
   - Выполняется тело конструктора `java.lang.Object`.
   - Для **базового класса**:
     1. Вычисляются инициализаторы полей экземпляра и выполняются блоки инициализации экземпляра (`{ ... }`) в порядке их следования в исходном коде.
     2. Выполняется тело конструктора базового класса.
   - Для **производного класса**:
     1. Вычисляются инициализаторы собственных полей экземпляра и выполняются блоки инициализации производного класса.
     2. Выполняется тело конструктора производного класса.

#### Опасность вызова полиморфных методов из конструктора (Пример 62 из пособия)
Если в конструкторе базового класса вызывается переопределяемый (виртуальный) метод:
- Динамическое связывание передаст управление в реализацию метода **производного класса**.
- Однако поля производного класса на этот момент **ещё не инициализированы** (содержат нули/null по умолчанию). Это приводит к логическим ошибкам или `NullPointerException`.
- **Правило**: из конструкторов безопасно вызывать только `private`, `final` или `static` методы.

```java
// Демонстрация порядка инициализации и передачи параметров в super(...)
class Base {
    int baseField = 10; // 1. Инициализация поля Base

    Base(int val) {     // 2. Тело конструктора Base
        System.out.println("Base constructor: baseField = " + baseField + ", param = " + val);
    }
}

class Derived extends Base {
    int derivedField = 20; // 3. Инициализация поля Derived

    Derived(int bVal, int dVal) {
        super(bVal);       // Вызов конструктора предка — строго 1-я строка
        this.derivedField = dVal; // 4. Тело конструктора Derived
        System.out.println("Derived constructor: derivedField = " + derivedField);
    }
}
```

## 2. Перегрузка и переопределение методов.

### 2.1. Перегрузка методов (Overloading)
- **Определение**: Объявление в рамках одного класса (или доступных из суперкласса) нескольких методов с **одинаковым именем**, но **различными сигнатурами**.
- **Сигнатура метода**:
  - Включает: **имя метода** и **список типов параметров** (их количество, типы и строгий порядок следования).
  - В сигнатуру **НЕ входят**: имена формальных параметров, возвращаемый тип, модификаторы доступа, секция исключений `throws`.
- **Связывание**: **Статическое** (*раннее*, compile-time). Конкретный перегруженный метод выбирается компилятором на этапе компиляции на основе типов аргументов вызова.
- **Ограничение**: Нельзя объявить два метода с одинаковым именем и одинаковым списком параметров, различающихся только возвращаемым типом или списком `throws` (ошибка компиляции).

---

### 2.2. Переопределение методов (Overriding)
- **Определение**: Замещение реализации нестатического метода суперкласса новой версией в производном классе с **точно такой же сигнатурой**.
- **Связывание**: **Динамическое** (*позднее*, runtime polymorphism). Выбор вызываемой реализации метода производится JVM во время выполнения программы на основе **фактического класса созданного объекта** в куче, а не типа переменной-ссылки (по таблице виртуальных методов — *vtable*).
- **Служебное слово `super`**: Внутри подкласса исходную версию метода базового класса можно вызвать через `super.methodName(...)`.

---

### 2.3. Правила и ограничения при переопределении
1. **Строгое совпадение сигнатуры**:
   - Имя метода и типы параметров обязаны точно совпадать. Случайное изменение типа параметра (например, `int` на `long`) создаст перегрузку вместо переопределения. Для контроля используется аннотация `@Override`.
2. **Ковариантность возвращаемых типов (Covariant Return Types)**:
   - Переопределяющий метод подкласса может возвращать **тот же тип либо его подтип** (сужение типа возвращаемого значения разрешено, начиная с Java 5).
   - Для примитивных типов и `void` возвращаемый тип обязан совпадать абсолютно точно.
3. **Модификаторы доступа (запрет сужения видимости)**:
   - Переопределяющий метод **не может сужать уровень доступа** по сравнению с базовым методом (принцип подстановки Лисков: клиент базового интерфейса не должен терять доступ к методу).
   - Расширение доступа разрешено:
     $$\text{private} \to \text{не переопределяется}; \quad \text{package-private} \to \text{package-private, protected, public};$$
     $$\text{protected} \to \text{protected, public}; \quad \text{public} \to \text{только public}.$$
4. **Контролируемые исключения (`throws`)**:
   - Переопределяющий метод **не имеет права объявлять новые или более широкие checked-исключения**, чем объявлены в базовом методе.
   - Разрешено: объявлять те же исключения, их подклассы, уменьшать число исключений или вовсе убрать секцию `throws`.
   - На непроверяемые исключения (`RuntimeException`, `Error`) данное ограничение не распространяется.
5. **Особые модификаторы**:
   - Методы `final` переопределять **запрещено**.
   - Методы `private` **не наследуются и не переопределяются**.
   - Статические методы (`static`) не участвуют в полиморфизме: они не переопределяются, а **скрываются** (*hiding*).

```java
class Animal {
    protected Animal reproduce() throws java.io.IOException {
        return new Animal();
    }
}

class Dog extends Animal {
    @Override
    public Dog reproduce() { // Расширен доступ (protected -> public),
        return new Dog();    // ковариантный возврат (Dog is Animal), убрано checked-исключение
    }
}
```

## 3. Сокрытие полей. Доступ к унаследованным членам. Возможность доступа и переопределение.

### 3.1. Сокрытие полей (Field Hiding)
- **Принцип**: В языке Java **поля не переопределяются — они могут только скрываться**. Динамического полиморфизма для полей не существует.
- **Суть сокрытия**: Если в производном классе объявляется поле с тем же именем, что и в базовом классе, поле базового класса продолжает физически существовать в объекте в памяти, но становится недоступным по прямому имени.
- **Статическое разрешение доступа к полям**:
  - Выбор поля при обращении через ссылку `ref.fieldName` всегда осуществляется **компилятором статически по объявленному типу ссылки**, а не по фактическому объекту в куче (байткод `getfield`).
  - При вызове виртуального метода `ref.methodName()` вызов всегда разрешается **динамически по реальному объекту**.

```java
// Пример 63 из пособия: разница между связыванием полей и методов
class SuperShow {
    public String str = "SuperStr";
    public void show() { System.out.println("Super.show: " + str); }
}
class ExtendShow extends SuperShow {
    public String str = "ExtendStr"; // Сокрытие поля str
    public void show() { System.out.println("Extend.show: " + str); } // Переопределение
}

SuperShow sup = new ExtendShow();
System.out.println(sup.str); // "SuperStr"  (статическое связывание по типу ссылки)
sup.show();                  // "Extend.show: ExtendStr" (динамический полиморфизм метода)
```

---

### 3.2. Доступ к скрытым полям
1. **Внутри производного класса**:
   - Через ключевое слово `super.fieldName` (доступ к полю непосредственного предка).
   - Через явное восходящее приведение ссылки: `((BaseClass) this).fieldName`.
2. **Из внешнего кода**:
   - Через явное приведение ссылки к базовому типу: `((BaseClass) derivedObj).fieldName`.
3. **Многоуровневое наследование**:
   - Синтаксическая конструкция `super.super.field` в Java **запрещена**.
   - Доступ к полю «дедушки» осуществляется через приведение ссылки: `((GrandParent) this).field`.

---

### 3.3. Доступ к унаследованным членам класса
В Java доступ определяется четырьмя модификаторами (проверка осуществляется на уровне классов, а не объектов):
- `private`: член доступен только внутри объявившего его класса. В производных классах недоступен напрямую (не наследуется логически, хотя физически присутствует в объекте).
- *package-private* (по умолчанию): доступен только внутри классов того же пакета. В подклассах из других пакетов недоступен.
- `protected`: доступен внутри своего пакета, а также **во всех производных классах** независимо от пакета.
  > **Важная тонкость (JLS §6.6.2)**: Производный класс из другого пакета может обращаться к `protected`-члену только через ссылку своего подтипа (или через `this`/`super`), но не через ссылку типа суперкласса на чужой объект.
- `public`: доступен повсеместно без каких-либо ограничений.

---

### 3.4. Возможность доступа и переопределение
- **Фундаментальное правило**: метод базового класса может быть переопределен только в том случае, если он **доступен** производному классу.
- **Псевдопереопределение `private`-методов**:
  - Если метод базового класса объявлен как `private`, подкласс «не видит» его.
  - Объявление в подклассе метода с точно такой же сигнатурой **не является переопределением** — это объявление абсолютно нового, независимого метода. Динамического полиморфизма не возникает. Аннотация `@Override` вызовет ошибку компиляции.
- **`package-private` методы при наследовании в другом пакете**:
  - Метод с доступом по умолчанию не виден классам других пакетов, поэтому одноименный метод в подклассе из другого пакета также не переопределяет его.

## 4. Сокрытие статических членов. Служебное слово super.

### 4.1. Сокрытие статических членов (Static Member Hiding)
- **Принадлежность классу**: Статические поля и методы (`static`) принадлежат классу в целом, а не конкретному объекту. Они хранятся в метаданных класса (Metaspace) и не имеют скрытого параметра `this`.
- **Отсутствие полиморфизма**:
  - Статические методы **не переопределяются, а скрываются** (*method hiding*). Они не вносятся в таблицу виртуальных методов (`vtable`).
  - Вызов статического метода через ссылку `ref.staticMethod()` компилируется в инструкцию `invokestatic` и **разрешается строго по объявленному типу ссылки на этапе компиляции**.
  - Если ссылка равна `null`, вызов `ref.staticMethod()` успешно выполнится без возникновения `NullPointerException`, если тип переменной-ссылки объявляет этот метод.
- **Правила совместимости статических и нестатических методов**:
  - Метод экземпляра **не может** переопределить статический метод предка (ошибка компиляции).
  - Статический метод **не может** скрыть метод экземпляра предка (ошибка компиляции).
  - Аннотация `@Override` на статическом методе запрещена.

---

### 4.2. Служебное слово `super`
Ключевое слово `super` предоставляет доступ к членам непосредственного суперкласса из нестатического контекста производного класса. Применяется в трёх случаях:

1. **`super(...)` — явный вызов конструктора базового класса**:
   - Обязан быть **первой строкой** конструктора подкласса.
   - Не может быть обернут в блок `try-catch`. Нельзя передавать `this` в качестве параметров.
2. **`super.fieldName` — доступ к скрытому полю суперкласса**:
   - Позволяет обойти сокрытие поля и обратиться к полю родителя с уровнями доступа `public`, `protected` или `package-private`.
3. **`super.methodName(...)` — вызов базовой реализации метода**:
   - Единственный способ вызвать оригинальную реализацию переопределенного метода предка.
   - В байткоде транслируется в инструкцию `invokespecial`, производящую прямой вызов метода в обход механизма полиморфной диспетчеризации (`vtable`).

---

### 4.3. Ограничения ключевого слова `super`
- **Запрет использования в статическом контексте**:
  - В статических методах, статических блоках инициализации и инициализаторах статических полей использовать `super` (как и `this`) категорически **запрещено**, так как статический контекст выполняется вне связи с конкретным экземпляром объекта.
- **Запрет цепочки `super.super`**:
  - Синтаксис `super.super.method()` или `super.super.field` в Java запрещен. Язык строго запрещает прямое вмешательство в реализацию прародителей в обход непосредственного родителя ради сохранения целостности инкапсуляции.

## 5. Совместимость. Явное преобразование типов.

### 5.1. Строгая типизация и совместимость типов
- Java — строго типизированный язык. Каждая переменная и выражение имеют фиксированный тип, известный на этапе компиляции.
- **Совместимость по присваиванию**: Переменной целевого типа `T` можно присвоить значение выражения типа `S`, если тип `S` совпадает с `T` или является его подтипом (подклассом).
- Литерал `null` совместим с любым ссылочным типом данных.

---

### 5.2. Восходящее преобразование (Upcasting / Расширение типа данных)
- **Суть**: Приведение ссылки производного класса к типу базового класса:
  ```java
  SuperClass ref = new SubClass(); // Upcasting
  ```
- **Свойства**:
  - Выполняется компилятором **автоматически и неявно**.
  - Является **абсолютно безопасным**, поскольку экземпляр подкласса всегда удовлетворяет контракту суперкласса (принцип подстановки Лисков).
  - С точки зрения интерфейса доступа происходит сужение: через ссылку `ref` можно вызвать только методы, объявленные в `SuperClass`, хотя вызываться будут переопределенные версии из `SubClass` (полиморфизм).
  - Любой ссылочный тип неявно приводится к корневому типу `java.lang.Object`.

---

### 5.3. Нисходящее преобразование (Downcasting / Сужение типа данных)
- **Суть**: Приведение ссылки базового типа к типу производного класса:
  ```java
  SubClass subRef = (SubClass) ref; // Downcasting
  ```
- **Свойства**:
  - Требует обязательного оператора **явного приведения типа**: `(TargetType) reference`.
  - Потенциально небезопасно, так как ссылка `ref` во время выполнения может фактически указывать на базовый объект или на объект другого параллельного подкласса.

---

### 5.4. Двухуровневый контроль приведения типов
1. **Контроль компилятора (Compile-Time)**:
   - Компилятор проверяет, состоят ли исходный и целевой типы в **одной ветви иерархии наследования**.
   - Приведение между заведомо несовместимыми ветвями (например, `(String) intObj`) вызывает ошибку компиляции (*inconvertible types*).
2. **Контроль виртуальной машины (Runtime RTTI)**:
   - В байткоде генерируется инструкция `checkcast`.
   - Во время выполнения JVM проверяет реальный тип объекта в куче. Если объект не совместим с целевым типом, выбрасывается исключение **`ClassCastException`**.

> **Преобразование ссылок vs примитивов**: Приведение ссылочных типов не изменяет сам объект в памяти — меняется лишь «угол зрения» компилятора на объект (тип ссылки определяет доступный набор методов и полей). Приведение примитивов физически конвертирует битовое представление значения в памяти.

---

## 6. Проверка типа.

### 6.1. Оператор `instanceof`
- **Назначение**: Бинарный оператор времени выполнения, позволяющий проверить, совместим ли фактический объект с указанным ссылочным типом данных.
- **Синтаксис**:
  ```java
  выражение instanceof ИмяТипа
  ```
- **Результат вычисления**:
  - Возвращает `true`, если объект, на который указывает выражение, является экземпляром указанного класса, его подкласса или реализует указанный интерфейс.
  - В противном случае возвращает `false`.
- **Поведение с `null`**:
  - Если левый операнд равен `null`, оператор **всегда возвращает `false`** без генерации исключения `NullPointerException`:
    ```java
    null instanceof AnyType // Всегда false
    ```
- **Проверка на этапе компиляции**:
  - Тип выражения и целевой тип обязаны быть потенциально совместимы в иерархии. Проверка заведомо независимых классов вызовет ошибку компиляции.

---

### 6.2. Идиома безопасного нисходящего приведения
Классический шаблон предотвращения `ClassCastException`:
```java
if (obj instanceof More) {
    More m = (More) obj; // Безопасно, ClassCastException исключён
    m.specificMethod();
}
```
*Начиная с Java 16*, поддерживается Pattern Matching для `instanceof`, совмещающий проверку и объявление переменной:
```java
if (obj instanceof More m) {
    m.specificMethod();
}
```

---

### 6.3. Сравнение `instanceof` и `getClass() == TargetClass.class`
| Характеристика | Оператор `instanceof` | Сравнение `obj.getClass() == Target.class` |
| :--- | :--- | :--- |
| **Учёт наследования** | Учитывает всю иерархию (возвращает `true` для подклассов) | Строго проверяет только точный класс (для подклассов `false`) |
| **Проверка интерфейсов** | Поддерживает (`obj instanceof MyInterface`) | Не применимо напрямую к интерфейсам |
| **Реакция на `null`** | Возвращает `false` без ошибок | Вызывает `NullPointerException` (при `obj == null`) |
| **Использование в `equals`** | Для классов без добавления новых полей состояния | Для иерархий, где подклассы расширяют состояние (защита симметрии) |

---

## 7. Методы и классы final.

### 7.1. Модификатор `final` для классов
- **Определение**: Класс, объявленный с модификатором `final`, **не может быть расширен** (запрещено наследование через `extends`).
  ```java
  final class NoExtending { /* ... */ }
  // class Sub extends NoExtending {} // Ошибка компиляции!
  ```
- **Свойства**:
  - Все методы `final`-класса неявно становятся `final`.
  - Поля класса автоматически `final` **не становятся** (их неизменяемость задается отдельно).
- **Применение в JDK**: Классы `String`, `Integer`, `Double`, `Math`, `System` объявлены как `final`.
- **Цели использования**:
  1. Создание гарантированно неизменяемых объектов (*immutable*).
  2. Безопасность системы: защита критических классов (например, подсистемы безопасности или String Pool) от подмены поведения злоумышленником через создание дочерних классов.

---

### 7.2. Модификатор `final` для методов
- **Определение**: Метод, помеченный модификатором `final`, **не может быть переопределен** в классах-потомках.
- **Цели использования**:
  1. **Защита контракта**: Гарантия того, что критически важный алгоритм не будет изменен или сломан в классах-наследниках.
  2. **Паттерн «Шаблонный метод» (Template Method)**: Каркасный метод объявляется как `final`, фиксируя скелет алгоритма, а отдельные шаги реализуются через переопределяемые методы.
  3. **Безопасная инициализация**: `final`-методы можно безопасно вызывать из конструкторов базового класса.
- **Особенность полей `final`-метода (правило пособия)**: Если метод объявлен как `final`, то поля, к которым он обращается, также должны быть `private` или `final`. В противном случае потомок сможет исказить логику метода через прямую мутацию открытых полей суперкласса.

---

### 7.3. Тонкости и оптимизация
- **Методы `private` неявно являются `final`**: Так как закрытые методы не видны потомкам и не могут быть переопределены, компилятор неявно считает их финальными.
- **Встраивание кода (Inlining)**: Для `final`-методов компилятор и JIT-компилятор JVM могут применять оптимизацию *инлайнинга* — подставлять тело метода непосредственно в точку вызова вместо генерации дорогого вызова `invokevirtual` и создания стекового кадра.
- **Взаимоисключение `abstract` и `final`**: Модификаторы `abstract` и `final` концептуально несовместимы. Класс или метод не может быть одновременно `abstract` и `final` (ошибка компиляции).

---

## 8. Методы и классы abstract.

### 8.1. Абстрактные классы (`abstract class`)
- **Определение**: Класс, объявленный с модификатором `abstract`, представляет собой обобщенную концептуальную заготовку для иерархии типов.
- **Запрет инстанцирования**: Нельзя создать экземпляр абстрактного класса оператором `new`:
  ```java
  abstract class Shape { /* ... */ }
  // Shape s = new Shape(); // Ошибка компиляции!
  Shape s = new Circle();   // Корректно (полиморфная ссылка)
  ```
- **Структура**: Абстрактный класс может содержать всё то же, что и обычный класс: поля любого доступа, конкретные методы, статические члены и **конструкторы**.
- **Конструкторы абстрактного класса**: Необходимы для инициализации полей базового класса и вызываются из конструкторов конкретных подклассов через `super(...)`.

---

### 8.2. Абстрактные методы (`abstract method`)
- **Определение**: Метод без тела реализации, определяющий имя, параметры, возвращаемый тип и исключения. Объявление завершается точкой с запятой `;` вместо фигурных скобок `{}`:
  ```java
  public abstract double getArea();
  ```
- Задает обязательный контракт поведения, который **обязаны реализовать неабстрактные классы-потомки**.

---

### 8.3. Фундаментальные правила для абстрактных сущностей
1. Если класс содержит хотя бы один абстрактный метод (собственный или унаследованный нереализованный), он **обязан быть объявлен как `abstract`**.
2. Абстрактный класс **может не содержать ни одного абстрактного метода** (применяется для запрета прямого создания объектов класса).
3. Производный класс, расширяющий абстрактный суперкласс, обязан либо **реализовать все абстрактные методы**, либо сам быть объявлен как `abstract`.
4. В производном классе разрешено переопределить конкретный метод суперкласса как абстрактный (для «аннулирования» некорректной базовой реализации).

---

### 8.4. Несовместимость модификаторов
Модификатор `abstract` для методов **не может сочетаться** со следующими модификаторами:
- `private` — абстрактный метод обязан быть виден потомку для реализации.
- `final` — абстрактный метод обязан переопределяться, а `final` запрещает переопределение.
- `static` — статические методы не участвуют в динамическом полиморфизме.
- `native`, `synchronized`, `strictfp` — относятся к деталям конкретной реализации метода.
Для классов: комбинация `abstract final class` запрещена.

---

### 8.5. Сравнение абстрактного класса и интерфейса
| Критерий | Абстрактный класс (`abstract class`) | Интерфейс (`interface`) |
| :--- | :--- | :--- |
| **Смысловая модель** | Отношение «является» (*is-a*), общая природа | Отношение «умеет делать» (*can-do*), контракт роли |
| **Модель наследования** | Одиночное наследование (`extends`) | Множественная реализация (`implements`) |
| **Состояние (поля)** | Любые поля экземпляра (`private`, `protected`, изменяемые) | Только константы (`public static final`) |
| **Конструкторы** | Имеются (вызываются через `super(...)`) | Отсутствуют |

---

## 9. Класс Object. Методы класса Object. Клонирование объектов.

### 9.1. Класс `java.lang.Object` в иерархии типов
- `java.lang.Object` является **корнем иерархии классов Java**. Если при объявлении класса ключевое слово `extends` не указано, компилятор неявно подставляет `extends Object`.
- Массивы всех типов являются полноправными объектами в JVM, напрямую наследуют `Object` и реализуют маркерные интерфейсы `Cloneable` и `Serializable`.
- Переменная типа `Object` способна хранить ссылку на объект любого типа или массива.

---

### 9.2. Методы класса `Object`
Класс `Object` содержит 11 методов (с учётом перегрузок):

1. `public String toString()`:
   - Возвращает строковое представление объекта.
   - По умолчанию возвращает: `ИмяКласса@хэшКод_в_16ричной_системе` (например, `Circle@15db9742`).
   - Вызывается неявно при строковой конкатенации `+` и передаче в `System.out.println()`.
2. `public boolean equals(Object obj)`:
   - Проверяет логическую эквивалентность объектов.
   - По умолчанию проверяет ссылочную идентичность: `this == obj` (указывают ли ссылки на один и тот же адрес в памяти).
   - **Контракт метода `equals`**:
     1. *Рефлексивность*: `x.equals(x) == true`.
     2. *Симметричность*: `x.equals(y) == y.equals(x)`.
     3. *Транзитивность*: если `x.equals(y)` и `y.equals(z)`, то `x.equals(z)`.
     4. *Согласованность*: повторные вызовы возвращают один результат, пока поля не изменились.
     5. *Сравнение с `null`*: `x.equals(null)` всегда возвращает `false`.
3. `public int hashCode()`:
   - Возвращает числовой 32-битный хеш-код объекта для эффективной работы в хеш-таблицах (`HashMap`, `HashSet`).
   - **Связь с `equals`**:
     - Если `x.equals(y) == true`, то `x.hashCode() == y.hashCode()` **(строго обязательно)**.
     - Если хеш-коды равны, объекты не обязательно равны по `equals` (коллизия хешей).
     - Если объекты не равны по `equals`, их хеш-коды желательно делать различными для производительности.
4. `public final Class<?> getClass()`:
   - Возвращает дескриптор класса объекта времени выполнения (`Class<?>`).
   - Объявлен как `final` (нельзя переопределить), вызов нативный.
5. `protected Object clone() throws CloneNotSupportedException`:
   - Нативный метод создания копии объекта.
6. `protected void finalize() throws Throwable`:
   - Метод очистки ресурсов перед сборкой мусора. Недетерминирован, устарел (`Deprecated` с Java 9, удален из активного использования в Java 18). Для очистки ресурсов используется `AutoCloseable` и конструкция `try-with-resources`.
7. `public final void wait()`, `wait(long timeout)`, `wait(long timeout, int nanos)`:
   - Переводят текущий поток в состояние ожидания на мониторе объекта с освобождением блокировки. Должны вызываться **строго внутри синхронизированного блока (`synchronized`) в цикле `while`**.
8. `public final void notify()`, `notifyAll()`:
   - Пробуждают один или все потоки, ожидающие на мониторе данного объекта. Вызываются строго внутри `synchronized`.

---

### 9.3. Клонирование объектов
- **Интерфейс `Cloneable`**:
  - Является **маркерным интерфейсом** (не содержит методов).
  - Служит сигналом для нативного метода `Object.clone()`: если объект класса вызывает `super.clone()`, не реализуя `Cloneable`, виртуальная машина выбрасывает исключение **`CloneNotSupportedException`**.
- **Поверхностное клонирование (Shallow Copy)**:
  - Выполняется нативным методом `super.clone()` по умолчанию: побитово копирует значения всех полей.
  - Поля примитивных типов копируются по значению.
  - Поля ссылочных типов копируются как адреса — оригинальный объект и его клон **разделяют одни и те же вложенные объекты**. Изменение вложенного объекта через клон исказит оригинал.
- **Глубокое клонирование (Deep Copy)**:
  - Создание независимой копии объекта вместе с **рекурсивным копированием всех изменяемых вложенных объектов**, на которые он ссылается.
  - Для неизменяемых полей (например, `String`, `Integer`) глубокое клонирование не требуется — ссылки на них безопасно разделять.

#### Канонический шаблон реализации глубокого клонирования в Java
```java
public class Person implements Cloneable {
    private String name;      // Неизменяемое поле — можно копировать ссылку
    private Address address;  // Изменяемый объект — требует глубокого копирования

    @Override
    public Person clone() {
        try {
            // 1. Поверхностное копирование примитивов и ссылок через super.clone()
            Person copy = (Person) super.clone();
            // 2. Глубокое копирование изменяемых ссылочных полей
            if (this.address != null) {
                copy.address = this.address.clone();
            }
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(); // Не должно произойти, т.к. Cloneable реализован
        }
    }
}
```

- **Альтернатива механизму `clone()`**:
  - Механизм `Cloneable` часто критикуется (в т.ч. Джошуа Блохом) за обход конструкторов и неуклюжую обработку исключений.
  - Лучшей практикой в современной разработке на Java является использование **копирующих конструкторов** (`public Person(Person other)`) или **статических фабричных методов копирования**.
